# Running it

For the shop, not for strangers. The app is one program that runs in a browser; this
page is where the commands, the checks and the deploy live.

## Commands

```
pnpm install
pnpm run dev        # http://localhost:5173 — the working copy
pnpm run build      # dist/ — what gets published
pnpm test           # unit + jsdom component tests
pnpm run e2e        # playwright: desktop, phone, firefox
pnpm run typecheck  # tsc over the app and the node-side scripts
pnpm run brand      # re-draw the icons and the in-app art from the shop's logo file
```

`pnpm run e2e` needs `dist/`, so `pnpm run build` first. Playwright starts its own
`vite preview` on port 4173 and reuses one already running.

## The four checks that sit outside the suites

They need a built or served copy, so they are not part of `pnpm test`.

| Command | What it proves |
| --- | --- |
| `node scripts/check-build.mjs /` | Everything the built page and the manifest point at resolves; the build output holds nothing that is not the app. Runs in CI at both bases. |
| `pnpm run check:worker` | The app does not reload itself, and a new version is offered rather than applied — and still applies when Reload is tapped. |
| `pnpm run probe:typing` | What one keystroke in a cell actually costs, in a real browser. |
| `pnpm run probe:keystrokes` | The same under churn — the probe that found the dialog lag, and the one that keeps it fixed. See `TASKS.md`. |

`check:worker` edits `src/main.tsx` to force a new bundle, rebuilds twice, and puts
the file back. Do not run it while another build is going.

## What a push does

Pushing to `main` runs `.github/workflows/deploy.yml`: the tests, then a build with
`VITE_BASE=/Production-App/`, then `scripts/check-build.mjs` at that base, then
publish `dist/` to Pages at `https://freo-stone.github.io/Production-App/`. The PWA
manifest and service worker are generated by the build, so the installed app and the
URL are the same program. A device picks up a new version when it is told: the offer
appears, and the page reloads when someone taps it.

## Where the data lives

| What | Where |
| --- | --- |
| Everything entered in the app | IndexedDB in the browser (`freo-production`) |
| The shared copy of that state | `state/state.json` in `Freo-Stone/Production-App-Data`, private |
| Stock on hand, open jobs | `exports/location.xlsx` and `exports/future.xlsx`, MYOB's reports mirrored into that same private repo |
| The app itself | `Freo-Stone/Production-App` — source and the built site, no data in either |

The browser is authoritative for writes; the repository is how the other devices find
out what changed. A push that collides comes back as a 409 and is merged after a
reread, so no device silently overwrites another. `docs/sync.md` walks each part.

## The shape of a day

1. Power Automate (or a manual download) drops the current MYOB exports into the
   private repo. The app pulls them and merges: stock rows replace, open jobs replace.
2. Production is entered against the day — line, product, trays. The curing clock
   starts.
3. Anything cured (and blasted, if it needs blasting) becomes ready stock.
4. On Friday, ready stock is listed for MYOB, keyed in, and marked entered. Until the
   next export from MYOB arrives, that stock is treated as counted. The weekday and
   the cut-off are settings; Friday is the default.

`TASKS.md` is the build plan and says which of those steps exist today.
